Q² × Salt × Chayne · technical session pre-read

Integrating Q² with a Salt-signed fund estate

Q² produces one exportable evidence chain per movement: who proposed it, which policy and fund context it was decided against, who approved it, what Salt checked and signed, what settled on chain and how it was booked. This document shows how a fund platform that already wraps the Salt SDK feeds that chain, and what the Q² API looks like.

API: designEvidence services: sandboxAudience: Salt engineering, Chayne platform

Overview

Every party in a fund's movement path already keeps its own truth. Salt is the source of signing truth. The chain is the source of settlement truth. Parsera is the source of ledger truth. None of them is the source of correlated truth, which is what an auditor, an LP in diligence or an examiner asks for. Today that join is assembled by hand.

Q² mints one identifier, the Movement Record ID (MRID), at the moment a movement is decided, before any signature exists. Every later fact attaches to it. The output is the Movement Evidence Chain: one artifact, exported in minutes, with no manual stitching.

Short version for Salt. Nothing changes in how Salt signs or enforces policy. The fund platform that wraps the Salt SDK makes two extra calls (one to Q² before runPoliciesCheck, one after submitTx) and relays transaction state as it changes. Q² never holds key material and never calls Salt to sign.

Who does what

ChayneOriginates and authorises every movement. Owns root and recovery authority.
Q²Decides eligibility against fund context, mints the MRID, records and seals the evidence.
SaltEnforces transaction-level policy, holds key shares, runs signing ceremonies.
ParseraRecords, reconciles and reports. The source of ledger truth.

No automation, including Q²'s, crosses from validation into origination. There is no bypass lane: a failed check never completes.

Movement Record and MRID

A Movement Record is created when the fund platform asks Q² to decide a proposed movement. It is append-only: facets are added as each party reports, never edited.

Movement Evidence Chain

The export for one MRID. It answers, in one document, the question every reviewer asks: was this movement authorised, under which policy, and did what happened match what was approved?

  1. Proposal. Who proposed what, from which account, to which destination, under which mandate.
  2. Eligibility decision. The fund context used (for example NAV-relative concentration limits Salt cannot see), the policy version and the result.
  3. Approvals. Each approver, the credential used, the time, and the quorum rule met. Separation of duties is checked: the credential that changed a policy cannot immediately execute under it.
  4. Salt policy check. Salt's PolicyCheck as returned: validated and rejected policies, with Salt's own timestamp.
  5. Signing and broadcast. Salt transaction id, state transitions, unsignedTxHash and the broadcast receipt.
  6. Settlement and ledger. The on-chain receipt and the Parsera ledger entry that booked it.
  7. Seal. The chain's head hash, sealed by Q², so tampering with any facet is detectable.

Formats: JSON (canonical, for machines and auditors' tooling) and PDF (for people). Both carry the same head hash.

Refusal Records

A refused movement is a first-class record with a reason code and no downstream facets. It proves a control fired, which a successful movement cannot. Refusals come from three places, and all three land in the same record type:

  • Q² eligibility, for example a concentration limit breached against live NAV (ELIG_CONCENTRATION_OBLIGOR).
  • Salt policy, when PolicyCheck.policyBreach is true; Salt's rejectedPolicies are copied in as returned (SALT_POLICY_BREACH).
  • Approval, when a quorum is not met before the decision expires (APPROVAL_EXPIRED), or an approver rejects it.

The seal

Each facet carries prev_hash (SHA3-256 over the canonical JSON of the previous facet), so the chain is tamper-evident. The head is sealed with hybrid classical and post-quantum signatures (NIST FIPS 204) and re-sealed as algorithms retire. The seal covers Q²'s records only. On-chain signatures produced by Salt remain classical, and nothing in this document changes them.

With the Salt SDK

Salt is an SDK. As Salt describes it, fund platforms wrap the SDK in their own API calls to record extra information or run additional approval flows before requesting signing. Q² attaches at exactly that point, inside the fund's wrapper, so Salt's code and policies do not change.

Who proposes and signs. Chayne's platform is the Salt proposer and signer. Its wrapper runs submitTx, listens for Salt's state updates (Salt sends them to the proposer at each stage) and passes them to Q² with the MRID attached. Q² is not a signer or user on the Salt account: it holds no key material, never signs and never originates a transaction.

Approvals. Salt confirmed on 21 Oct that the nominated approver check runs at the proposing stage. The public SDK reference still describes nominated_approvers as not yet enforced, so we are confirming the current status with Salt. Either way, Q² records the quorum decision before submitTx, and records Salt's approver check as part of the evidence once its status is confirmed.

The wrapper pattern

Below, the Chayne wrapper around the Salt SDK. Salt method names are from the public SDK reference; check the Salt docs for exact parameters of submitTx. The Q² client is illustrative and follows the draft API.

import { Salt } from "@kagamidigital/salt-sdk-mirror";
import { Q2 } from "./q2-client";            // draft client for the API below

const salt = new Salt({ environment: "TESTNET", domain: "sandbox.chayne.example" });
const q2 = new Q2({ apiKey: process.env.Q2_SANDBOX_KEY });

export async function moveFunds(req) {
  // 1. Decide before anything is signed. Q² mints the MRID here.
  const mv = await q2.movements.create({
    entity: "fund:chayne-master",
    proposer: req.proposer,
    mandate: req.mandate,
    policyVersion: req.policyVersion,
    action: { accountId: req.accountId, chainId: req.chainId, to: req.to, asset: req.asset, amount: req.amount },
    context: { navSnapshotRef: req.navSnapshotRef },   // a reference, never investor PII
  });
  if (mv.decision.status === "refused") return mv;  // Refusal Record already written

  // 2. Wait for the quorum (people, or a policy they signed). Fails closed on expiry.
  const approved = await q2.movements.waitForApproval(mv.mrid);
  if (approved.decision.status !== "approved") return approved;

  // 3. Salt checks its own transaction-level policies, unchanged.
  const check = await salt.runPoliciesCheck(req.accountId, req.txParams);
  if (check.policyBreach) return q2.movements.refuse(mv.mrid, { code: "SALT_POLICY_BREACH", saltPolicyCheck: check });

  // 4. Submit to Salt and bind Salt's transaction id to the MRID.
  const tx = await salt.submitTx(/* see Salt docs */);
  await q2.movements.attachSalt(mv.mrid, tx);          // id, state, policyCheck, unsignedTxHash, metadata
  await db.mridBySaltTx.put(tx.id, mv.mrid);          // the wrapper keeps the mapping
  return { mrid: mv.mrid, saltTransactionId: tx.id };
}

// 5. Relay Salt state changes as they happen. Salt sends them to the proposer at each stage;
//    Salt will share example listener code. Event name and payload to confirm.
salt.subscribeToUserEvent("transaction", async (evt) => {
  const mrid = await db.mridBySaltTx.get(evt.id);
  if (mrid) await q2.movements.saltState(mrid, await salt.getTransaction(evt.id));
});

Carrying the MRID

The single most important integration question. Three options, best first:

OptionHowEvidence strength
A. Wrapper mapping (proposed default)The Chayne wrapper stores salt.id ↔ mrid at submitTx and reports both to Q². No Salt change. Matches Salt's note that the object can be extended inside the Chayne platform code.Strong. Binding is recorded at submission, before signing.
B. Native referenceSalt carries an external reference on the transaction and returns it on its events.Strongest. The MRID appears in Salt's own record.
C. Fallback matchCorrelate by unsignedTxHash, broadcast hash, address, amount and time window.Workable, weaker and heavier to build.

With Parsera

Read only, no investor PII at any point. Q² needs two things from Parsera: fund context for eligibility (NAV and obligor identity at the needed granularity) and the ledger entry that booked a movement, ideally indexed by an external reference (the MRID) or else by transaction hash. Scope to be agreed in the Parsera read-API session. Until then the sandbox runs on a synthetic context model.

API (draft)

REST over HTTPS, JSON bodies, base URL https://api.sandbox.q2.example/v0 (placeholder). Bearer API keys, one per environment and tenant. Every write is idempotent with an Idempotency-Key header. Design

POST/v0/movements

Propose a movement and get an eligibility decision. Mints the MRID. Returns 201 for both eligible and refused decisions; a refusal is a result, not an error.

POST/v0/movements/{mrid}/approvals

Record an approval or rejection by a named approver. The proposer cannot approve. When the quorum is met, the decision moves to approved.

{ "approver": "person:op-partner", "verdict": "approve", "credential": "passkey:opp-02" }
POST/v0/movements/{mrid}/salt

Attach the Salt AccountTransaction returned by submitTx, unmodified. Q² checks params against the approved action and refuses on mismatch (PARAMS_MISMATCH).

POST/v0/movements/{mrid}/salt/state

Report a Salt state change (the latest AccountTransaction from getTransaction). Appends a salt.state facet.

POST/v0/movements/{mrid}/refusal

Record a refusal raised outside Q², for example a Salt policy breach. Closes the record with a reason code.

GET/v0/movements/{mrid}

Current state of a Movement Record and its facets.

GET/v0/movements/{mrid}/evidence-chain?format=json|pdf

Export the Movement Evidence Chain. Target: available within minutes of the last facet, no manual step.

GET/v0/movements?entity=…&from=…&to=…&status=refused

List records for a period, for example every refusal last quarter, for an auditor or examiner.

Webhooks

Signed with HMAC-SHA256 in Q2-Signature, retried with backoff, delivered at least once (deduplicate on event_id). Design

approval.stalledNo quorum within the alert window. An alert, never a silent queue.

Sandbox and tenants

  • Q² sandbox runs on synthetic data, with no touch on Chayne, Salt or Parsera systems. Phase 1 is built here, negative path first.
  • Salt test tenant. Salt segregates data by tenant id and creates a tenant that accepts authentication from a supplied domain (SIWE). We will send Salt the sandbox domain for the Chayne wrapper.
  • Environments. Salt TESTNET for attachment tests. Mainnet only in the pilot phase, on a read-only shadow feed first.

Security boundaries

  • Q² holds no keys, key shares, signing credentials or funds, under any integration pattern.
  • Q² never calls Salt to sign or originate. It only receives what the wrapper reports.
  • Fail closed: missing context, an expired decision or an unreachable Q² means the movement does not proceed. The read and export plane stays available when the decision plane is not.
  • No investor PII leaves Parsera. Context is passed by reference.
  • Data residency, retention (five years, first two readily accessible) and the subprocessor list are set in Phase 0.
